# 仓库级协作说明

用于减少常见 LLM 编码失误的行为准则。可与项目专属说明合并使用。

**权衡：** 这些准则偏向谨慎而非速度。对于简单任务，请自行判断。

## 1. 编码前先思考

**不要假设。不要隐藏困惑。把权衡摆到台面上。**

实现前：

- 明确说明你的假设；不确定时，先问。
- 存在多种理解时，先列出来，不要默默选一种。
- 有更简单方案时，要说出来；必要时可以 push back。
- 不清楚的地方，先停下来，点明困惑，再提问。

## 2. 简单优先

**用最少代码解决问题。不要 speculative。**

- 不做需求之外的功能。
- 不为一次性代码抽象。
- 不加未被要求的“灵活性”或“可配置性”。
- 不为几乎不可能的场景写错误处理。
- 写了 200 行但 50 行就够，就重写。

问自己：“资深工程师会不会觉得过度设计了？” 如果是，就简化。

## 3. 精准改动

**只动该动的。只清理自己造成的遗留。**

编辑现有代码时：

- 不要“顺手”改相邻代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有风格，即使你个人偏好不同。
- 发现无关死代码，可以提一句，但不要删。

当你的改动产生孤儿代码时：

- 删除**你的改动**导致未使用的 import/变量/函数。
- 不要删除改动前就存在的死代码，除非被要求。

检验标准：每一行改动都应能直接追溯到用户请求。

## 开发库验证规则

Codex 仅可在开发验证场景下查询开发库。

数据库用户为：

d_aicontract_opr

Codex 仅可执行：

- SELECT
- SHOW
- EXPLAIN

Codex 不得执行：

- INSERT
- UPDATE
- DELETE
- DROP
- ALTER
- TRUNCATE
- CREATE
- GRANT
- REVOKE
- REPLACE
- MERGE
- CALL
- EXECUTE

Codex 必须使用以下任一批准方式：

1. 项目级 MCP 服务器：

dev_db

2. 备用脚本：

./scripts/db/query.sh < scripts/db/check_xxx.sql

Codex 不得：

- 打印数据库密码；
- 修改 `.env.local`；
- 自动创建 `.env.local`；
- 查询生产库；
- 查询预生产库；
- 查询 UAT 库；
- 查询无关业务库；
- 执行不带 `LIMIT` 的探索性 SELECT 查询。

数据库写入仅可通过以下方式触发：

- 业务 API；
- 本地页面；
- 自动化测试。

Codex 不得直接写入数据库。

验证持久化逻辑时，Codex 应报告：

1. 受影响的表；
2. 使用的 SQL；
3. 预期结果；
4. 实际结果；
5. 验证结论。

## 数据库变更记录规则

修改 `app-knowledge-service` 代码时，任何 AI Agent 都必须检查该变更是否需要记录数据库 SQL。

以下情况必须记录 SQL：

- 表结构变更；
- 索引变更；
- 默认值或约束变更；
- 字典、模板、配置或种子数据变更；
- 部署所需的跨服务配置数据，例如本服务使用的 `common_proxy` 记录。

以下情况通常不需要记录 SQL：

- 运行时流程产生的正常业务数据；
- 临时本地测试数据；
- 仅由自动化测试生成的数据。

版本化 SQL 的默认存放路径为：

app-knowledge-service/src/main/resources/sql

SQL 记录规则：

- 可部署的变更应使用新的版本化 SQL 文件；
- `INSERT` 语句应使用显式列清单；
- 不得插入自增 `id` 值；
- 部署时间戳优先使用 `NOW()` 或数据库端默认值，除非需要固定历史时间戳；
- 在可行时保持 SQL 幂等，例如使用 `INSERT IGNORE` 或存在性检查；
- 当代码变更需要 SQL 时，应在最终回复中说明对应的 SQL 文件。

## 平台版本与发布文档

- 知识库管理平台版本历史的权威入口：`docs/versions/版本历史.md`。
- 每次上线单独建立 `docs/releases/V{版本号}/`，内含上线配置单及 SQL 等相关附件。
- 前后端共同发布时，本仓库文档作为平台级发布入口；前端仓库 `app-knowledge-web` 应引用同一路径，避免分别维护两套版本口径。
- 版本内容必须以 Git 提交、Tag、SQL、现有设计/测试文档为依据；未生成的 Tag、镜像号和生产配置必须标记为“待确认”，不得推测填写。
