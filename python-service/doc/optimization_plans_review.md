## 二、具体问题

### 问题 1：两份方案的关系没有定义清楚

> [!WARNING]
> 两份文档有大量内容重叠但组织方式不同，容易让团队不知道该跟哪份。

重叠内容对照：

| 主题 | 流程分层版位置 | 准确率版位置 | 差异 |
|------|--------------|-------------|------|
| LLM 查询改写关闭 | §12 查询理解层 | §2.1 P0 | 准确率版更具体（50 字符阈值），流程版更泛 |
| 父子检索扩展 | §4 多粒度 chunk 层 | §2.5 P1 | 流程版设计更深入（EvidenceGroup 拆分），但准确率版给了预期收益 |
| 证据对齐 LCS | §2 文档解析层 | §2.8 P1 | 基本一致，准确率版代码更完整 |
| RRF 融合 | §13 多通道召回层 | §2.3 P0 | 准确率版给了具体代码，流程版更强调意图权重 |
| 受约束 Schema | §7 知识结构层 | §2.13 P2 | 基本一致 |
| 中文正则关系 | §7 知识结构层 | §2.12 P2 | 基本一致 |
| 实体去重五阶段 | §7 知识结构层 | §2.14 P3 | 基本一致 |

**建议**：明确两份文档的关系——准确率版作为**执行路线图**（what to do & when），流程分层版作为**架构参考手册**（how to do & why）。在两份文档开头互相引用，并注明各自定位。

### 问题 2：预期收益数字过于乐观，且存在重复计算

> [!CAUTION]
> 准确率版的收益预估存在严重的**加法谬误**。

准确率版预估：

| 阶段 | 预期命中率 | 隐含增量 |
|------|-----------|---------|
| 当前 | 80.0% | — |
| Phase 1 | 85~88% | +5~8% |
| Phase 2 | 92~95% | +7~12% |
| Phase 3 | 97%+ | +2~5% |

但逐项相加的话：
- P0: +3~5% + 2~3% + 2~3% = **+7~11%**
- P1: +5~8% + 3~5% + 3~4% + 3~5% = **+14~22%**
- P2+P3: 若干项

**总计隐含增量远超 20%**，但实际收益之间是有重叠的：
- **查询改写关闭**和**口语同义词扩展**会互相覆盖一部分受益样本
- **产品映射**和**制度 profile 优化**针对的部分也有交集
- **RRF 融合**和**通道权重调整**本质上改的是同一个融合逻辑

更合理的预估方式：
- Phase 1 做完后跑一次 315 题测试，拿实际数字
- Phase 2 每做完一项跑一次回归测试
- 每项优化的预期收益应标注"独立增量"还是"联合增量"

**建议**：在准确率版中增加一节"收益估算假设与风险"，说明各项之间的重叠关系，并将 Phase 结束目标改为区间（如 83~86%），而不是直接叠加。

### 问题 3：流程分层版缺少验证闭环

> [!IMPORTANT]
> 09_flow_layer 有 21 节内容，但没有一节专门讲"怎么验证改完后确实变好了"。

准确率版至少有 315 题测试集和消融测试作为基准。但流程分层版提出的很多改动（如文件缓存、line span、结构块保护、Anchor 去重）都是工程改进，缺少验证标准：

| 改动 | 流程分层版说的效果 | 缺少的验证 |
|------|-----------------|-----------|
| 文件缓存 | "速度会明显提升" | 缺少基准时间和目标时间 |
| line span | "前端可以行级高亮" | 缺少覆盖率指标（多少文件能产出 line bbox） |
| 结构块保护 | "表格不容易被切碎" | 缺少 chunk 质量评估标准 |
| Anchor 去重 | "别名更容易合并" | 缺少 precision/recall 目标 |
| 图谱 Schema | "噪声降低" | 缺少 reject rate 的合理区间 |

**建议**：
1. 在流程分层版第 10 节（质量报告）中，为每个改动层建立**最小验证标准**
2. 或者在第 18 节（实施顺序）的每批里加上"验收条件"

### 问题 4：产品名映射方案（§2.4）设计偏简单

准确率版认为产品名映射是"最大的单一瓶颈"（影响 35~62% 的错误结果），但给出的方案只是一个简单的 keyword filter boost：

```python
product_names = extract_product_names(file_node_name)
# 例："鲁农担批〔2025〕23号 鲁担惠农贷_加工贷" → ["加工贷", "鲁担惠农贷"]
```

问题在于：
1. **产品名提取只从文件名**——如果文件名不规范（如"2025年第3批方案.pdf"），就提取不出产品名
2. **没有处理一个文件包含多个产品**的情况（如综合方案文档）
3. **用户问法和产品名之间的模糊匹配**——用户可能说"惠农"而不是"鲁担惠农贷"
4. **没有和流程分层版§7 的 Anchor 体系打通**——产品名本质上就是一个 Product 类型的 Anchor

**建议**：
- 产品名提取应同时从**文件名 + 正文标题 + 字段抽取结果**三个来源合并
- 产品名到文件的映射应该写入一张显式的映射表（MySQL），而非只靠 ES 字段
- 和 Anchor 去重统一管理产品别名

### 问题 5：流程分层版的"第一批"和准确率版的"Phase 1"不一致

| 准确率版 Phase 1（1~2 周） | 流程分层版第一批 |
|--------------------------|-----------------|
| 关闭 LLM 改写 | ✅ 短查询不改写 |
| 调整融合权重 | ✅ 切到 weighted_rrf |
| 修复 BM25 归一化/RRF | ❌ 未提及 |
| — | ✅ 父子上下文扩展 |

准确率版 Phase 1 不包含父子扩展（放在 Phase 2），但流程分层版认为这是第一批就该做的。反过来，准确率版 Phase 1 包含 BM25 归一化修复（span=0 时分数虚高），流程分层版没有专门提这个 bug。

**建议**：统一实施顺序。我的判断是准确率版的排序更合理，因为：
- BM25 归一化修复是**纯 bug fix**，改动最小，收益确定
- 父子扩展涉及 EvidenceGroup 结构变更，改动面更大，放 Phase 2 更稳

### 问题 6：部分代码示例有逻辑或风格问题

#### 6a. 准确率版 §2.1 的短查询判断逻辑有冗余

```python
def should_enhance_query(query: str) -> bool:
    if len(query) <= 50:
        return False
    if len(query) <= 4:    # ← 永远不会走到这里，因为上面已经排除了 <=50
        return False
    return True
```

`len(query) <= 4` 的分支在 `len(query) <= 50` 之后永远不会执行。应该反过来：

```python
def should_enhance_query(query: str) -> bool:
    if len(query) <= 4:
        return False  # 超短查询用同义词表
    if len(query) <= 50:
        return False  # 短查询保持原样
    return True
```

或者更好的写法是把两个条件合并，因为效果一样（都返回 False）。

#### 6b. 准确率版 §2.15 坐标追溯的 fuzzy_match 是 O(n²)

```python
for line in chunk_lines:
    for line_no, coord in coord_map.items():  # ← 对每个 chunk line 遍历整个 coord_map
        if line_no not in used_indices and fuzzy_match(line, get_line_text(line_no)):
```

如果 coord_map 有 10000 行，chunk 有 100 行，这就是 100 万次 fuzzy_match。应该用 hash + 回退策略。

#### 6c. 流程分层版的 `should_rewrite_query` 同样存在逻辑问题

```python
def should_rewrite_query(query: str) -> bool:
    q = query.strip()
    if len(q) <= 50:
        return False
    if looks_like_exact_field_query(q):   # ← 这些函数未定义
        return False
    if contains_product_name_and_field(q): # ← 这些函数未定义
        return False
    return True
```

这里 `looks_like_exact_field_query` 和 `contains_product_name_and_field` 没有给出实现，但它们对行为影响很大。如果这些函数判断过宽，会导致长查询也不被改写。

**建议**：给出这两个函数的最小实现，至少用正则或关键词匹配。

### 问题 7：流程分层版篇幅过长，优先级信号不足

1629 行、21 节的文档在工程团队中很难被通读。虽然第 0 节有总览表，第 18 节有实施顺序，第 19 节有"最先落地的 5 个包"，但：

- 第 0 节总览表给了 P0/P1/P2，第 18 节给了"第一批到第五批"，第 19 节又给了"5 个代码包"——三套优先级体系
- 读者不确定应该跟哪一套
- 第 1 节到第 17 节之间的内容对于不同优先级的读者来说信息密度差异很大（有些节是 P0，有些是 P2+）

**建议**：
- 在每节标题里直接标注优先级，如"§4. 多粒度 chunk 层【P0】"
- 或者把第 0 节的表格做成可跳转链接，让读者按优先级阅读

### 问题 8：两份方案都缺少"不做什么"的声明

> [!TIP]
> 好的技术方案不只说做什么，还要说**明确不做什么**，避免范围蔓延。

例如：
- 是否考虑换 ES 版本或引入 Milvus？（准确率版提到了稀疏向量，但没说是否需要换向量库）
- 是否考虑重训 embedding 模型？（两份方案都没提）
- 是否考虑多语言支持？
- 是否考虑 fine-tune reranker？
- 前端改造是否在本期范围内？

流程分层版第 20 节的"不建议照搬"很好，但那是对参考项目的，不是对自己项目的 scope 控制。

### 问题 9：消融测试结论的解读可能需要复核

准确率版 §1.3 的核心结论是"去掉功能反而更好"，据此大幅降低了 graph 和 structured 通道权重。但：

| 配置 | 命中率 | 变化 |
|------|--------|------|
| baseline | 56.0% | — |
| no_graph | 59.3% | +3.3% |
| no_structured | 59.7% | +3.7% |

这个测试只在 **110 题**上做的（全集 315 题的一个子集），而且 baseline 命中率只有 56%（远低于全集的 80%）。这说明：

1. **110 题子集可能偏向于 graph/structured 表现差的品类**（如制度类），不能代表全集
2. **3.3% 的差异在 110 题上只相当于 ~3.6 个题**，统计显著性不足
3. graph 和 structured 通道可能在某些品类（如字段查询、关系查询）是正面贡献，只是被制度类拖了均值

**建议**：
- 在全集 315 题上补跑 `no_graph` 和 `no_structured` 消融
- 或至少按品类分别看 graph/structured 的贡献

### 问题 10：流程分层版的置信度公式需要校验

§6.3 给出的字段置信度公式：

```python
confidence = (
    0.35 * source_score       # 0~1
    + 0.30 * evidence_score   # 0~1
    + 0.20 * chunk_score      # 0~1
    + 0.15 * consistency_score # 0~1
)
```

以及 §14.3 的检索置信度：

```python
confidence = 0.6 * top_score + 0.4 * average_top_scores
```

这两个公式的输入值域需要确认。如果 `source_score` 的定义是"来自强规则=1.0, 弱规则=0.7, LLM=0.5"，那和 `evidence_score`（exact=1.0, normalized=0.8, fuzzy=0.5, failed=0.0）的尺度是一致的。但 `chunk_score` 如果直接用 BM25 或 RRF 分数，值域可能不在 [0,1]。

**建议**：明确每个子分数的定义和值域，或者在公式前加 min-max 归一化（但要避免犯 §2.3 自己提到的 span=0 问题）。
